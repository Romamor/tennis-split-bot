# Замечания к первой версии: сверка со второй

10 сентября 2026. Основание: сообщения пользователя в этой задаче, прежние ревью,
утверждённый макет и код второй версии после исправления личного меню и персональной панели.
Повторяющиеся замечания объединены. Короткие ответы без исходного вопроса
не превращены в новые требования по догадке.

Это сверка требований и предложение следующей работы. Исправления из списка ниже
не считаются сделанными только потому, что описаны здесь. Текущая установка —
в [DEPLOYMENT_STATUS.md](DEPLOYMENT_STATUS.md).

**Порядок работы после уточнения пользователя:** сначала сверить все блоки, затем
дождаться отдельной команды отправить согласованный пакет на сервер. Не выкладывать
правки по ходу обсуждения. Текущая установка и подготовленные изменения разделены
в DEPLOYMENT_STATUS. Решение по навигации: при выходе с неподтверждёнными изменениями предупреждать
и предлагать «Продолжить ввод» или «Сбросить и выйти». Без изменений возвращаться
без предупреждения. Реализовано локально, без выкладки. Решения по главному меню и переводам зафиксированы ниже; сверка продолжается.

## Решения текущей сверки — реализованы локально

- **Выход из ввода:** при несохранённых изменениях предложить «Продолжить ввод»
  или «Сбросить и выйти». Без изменений возвращаться без предупреждения.
- **Главное меню в личке:** у участника только «🏓 Мои тренировки» и «💰 Мои расчёты».
  Администратору дополнительно «➕ Создать тренировку» и «📋 Управление тренировками»;
  суперадминистратору «👥 Администраторы бота». «🔄 Сменить группу» только при нескольких группах.
  Создание остаётся отдельным пунктом. Запись и история переводов — внутри «Моих расчётов».
- **Мои расчёты:** упрощённые предложения взаиморасчётов сохраняются. Можно записать
  произвольный реальный перевод «я отправил участнику» или «я получил от участника»
  выбранной группы, независимо от предложений и текущих долгов, включая аванс.
- **Возможный дубль:** перед записью искать в этой группе перевод с теми же отправителем,
  получателем и суммой, записанный за последние 24 часа (скользящее окно, а не календарный день).
  Автор предыдущей записи может быть другой стороной перевода. Показать совпадение
  и предложить вернуться либо подтвердить, что это ещё один реальный перевод.
  Не блокировать совпадения автоматически и не сохранять новую запись до подтверждения.
  Окно по времени записи — рабочее уточнение для реализации; дату фактического перевода не подменять.

- **Исправление суммы перевода:** пользователь согласовал прямую кнопку «Исправить сумму»
  для обеих сторон перевода. Обновлять существующую запись, сохранять прежнюю сумму
  в истории и корректировать влияние на баланс. У второй стороны остаётся «Уточнить перевод».
  Реализовано локально, без выкладки. Правило выхода из несохранённого ввода
  распространяется и на эту форму; окончательная правка требует подтверждения.

- **Завершение уточнения перевода:** согласовано — только начавший уточнение выбирает
  «Всё верно» или «Отменить запись». Во время уточнения перевод не влияет на баланс.
  Обе стороны могут исправлять сумму, но правка сама по себе не снимает уточнение
  и не возвращает влияние на баланс. Это правило нужно сохранить при реализации
  прямой правки суммы и проверить отдельным сценарием.

- **Управление тренировкой:** согласованы названия «🧮 Учесть тренировку» для открытой,
  «✏️ Исправить тренировку» для учтённой, «✅ Применить правки» при исправлении.
  Пока правки не применены, действует прежний расчёт. Перед применением показывать
  результат и запрашивать подтверждение. «🗑 Отменить тренировку» — отдельное действие
  с подтверждением; оно снимает влияние тренировки, сохраняя реальные переводы.
  Названия и финансовое правило реализованы локально.

- **История изменений:** согласован короткий формат с автором, временем по часовому
  поясу группы и только изменёнными полями «до → после». Одна запись на подтверждённую
  правку; кнопки и перелистывания не являются изменениями. Для массового добавления
  показывать несколько имён и «ещё N», для учёта — итоговую сумму тренировки.
  История постраничная; ограничение длины сохранять при любых длинных именах и пачках.
  Новый формат «до → после» и местное время реализованы локально.

- **Баланс группы:** пользователь выбрал «Имя · баланс: +300 ₽» и «Имя · баланс: −300 ₽».
  Кнопка нулевых значений называется «⚖️ Нулевой баланс». Сортировка по посещаемости
  в выбранной группе и пагинация сохраняются. Слова «долг» и «должен» не использовать
  в текстах и кнопках бота; это ограничение не касается обсуждения с пользователем.
  Прежние макеты с «получить / перевести», стрелками и другими вариантами подписей
  не являются согласованным решением. Ненулевой баланс сохраняется после выхода из группы;
  нулевые показываются только для ранее участвовавших людей.
- **Одинаковые имена:** согласовано показывать имя и фамилию, при совпадении добавлять
  @username. Если различить аккаунты всё равно нельзя, дать открыть профиль Telegram
  перед выбором. Различимость проверять по всему соответствующему списку, а не только
  по текущей странице. Ручное имя в группе пока остаётся запланированной функцией.
  Подписи должны учитывать обрезку длинных имён; отображение ссылки на профиль
  зависит от доступности аккаунта и клиента и требует проверки при реализации.

- **Порядок во время выбора:** согласовано фиксировать порядок игроков на весь текущий
  выбор, включая перелистывание. Новая сортировка по посещаемости применяется при
  следующем открытии списка. Параллельные изменения не должны перемещать имена между
  страницами. Уже добавленных другим участником не добавлять повторно и не сбрасывать их данные.
- **Эффективность:** вернуть обновление посещаемости при изменении данных вместо
  пересчёта на чтении и пакетную запись кнопок одного сообщения. Сохранить действующие
  правила жизни кнопок. Сравнить число запросов и записей на пользовательские действия.

## Проверка согласованного пакета

Локальная сборка: 73 проверки. На сервер пакет не установлен. Перечень постоянных
сценариев и границ автоматических проверок — в [UI_REGRESSION_SCENARIOS.md](UI_REGRESSION_SCENARIOS.md).
Подготовка карточки в измеряемом сценарии: 8 отдельных транзакций записи заменены одной.
Чтение состава не сканирует training_players для пересчёта посещаемости.
Далее по запросу пользователя — масштабное ревью, рефакторинг для экономии места,
размер и прогноз роста базы, способы резервного копирования. Выкладка и очистка сервера
остаются запрещены до отдельной команды.

## Как читать статусы

- **Сохранено:** есть соответствующий путь в коде; это не означает проверку всех клиентов Telegram.
- **Частично:** данные или отдельный путь есть, но требование целиком не закрыто.
- **Регрессия:** прежнее полезное поведение потеряно при переписывании.
- **Изменено:** позднейшая договорённость заменяет старое решение.
- **Запланировано:** пользователь явно согласовал поля или направление без реализации интерфейса.
- **Проверить в клиенте:** автоматических проверок недостаточно для вывода об отображении.

## Уточнение после первоначальной сверки

**R63.** Пользователь выбрал основную кнопку «Играл» и отказался от отдельной «Мои данные». Повторное нажатие играющего открывает его управление без сброса времени и суммы. Кто играл, но не оплатил стол, оставляет 0 ₽. Новый ввод оплаты требует участия. «Не играл» при ненулевой оплате требует подтвердить удаление показанной суммы; реальные переводы сохраняются. Это более позднее правило заменяет допущение об оплате стола без игры и соответствующие старые тестовые ожидания; авансы и реальные переводы между людьми остаются независимыми. | R72 | В меню администраторов не видно роли | Действующие администраторы показаны с ролями. Кандидаты на назначение — отдельно; назначение можно снять, роль Telegram объяснена |
| R73 | После сохранения нужен понятный вход для отмены участия и правки времени/оплаты | Общая карточка имеет одинаковую клавиатуру для всех: «Участие». В личной карточке до записи «Играл», после — «Изменить участие». Повторный вход не сбрасывает сохранённые данные |
| R74 | Администратор должен добавлять любого участника группы независимо от прежних тренировок | «Игроки» показывает всех известных аккаунтов этой группы без фильтра прошлых посещений. «Найти в Telegram» добавляет отсутствующий аккаунт. Оба пути проверены до сохранения участия и на изоляцию групп; полная автоматическая загрузка списка группы недоступна через Bot API |

**R75.** Администратор подтвердил массовое добавление. В «Игроки» виден состав текущей тренировки
со временем, оплатой и +1. «Участники группы» показывает остальных известных боту людей,
независимо от посещений; отметки сохраняются на разных страницах и после перезапуска.
«Добавить · N» выполняет одну атомарную команду `AddPlayers`: по 1 ч, 0 ₽, без гостя.
В истории это короткая запись с числом добавленных игроков. Проверка восьми добавлений
по 27 человек защищает страницу истории от превышения лимита Telegram.
До подтверждения меняется только личный выбор в `bot_sessions.input_json`; новых таблиц нет.
Уже играющие повторно не предлагаются и не сбрасываются. Изменение тренировки во время выбора
требует повторной проверки; права администратора проверяются в этой группе.
«Добавить человека» позволяет дополнить список реальным аккаунтом и вернуться к выбору.
После правки игрока сохраняется страница состава. Живое отображение на Mac не проверено автоматически.

Последние уточнения этого пакета: выбор человека администратором уже означает участие,
поэтому после «Добавить · N» отдельного «Играл» нет. Общие кнопки «Участие» и
«Открыть у бота» размещены в одной строке. Ссылка из стартового сообщения ведёт
в меню группы, ссылка из карточки — в конкретную тренировку в личке.
Статус после применения расчёта называется «Учтена» / «Тренировка учтена»: это
означает включение расчёта в балансы. Смысл операций и проводки не меняются.

## Что позднее заменило старые решения

1. «Добавить по имени и привязать к аккаунту» заменено настоящими Telegram ID.
   Возвращать псевдопользователей ради старого экрана не нужно.
2. «Любой участник редактирует всю тренировку» заменено ролями администратора
   и самостоятельной правкой собственной строки.
3. Массовый выбор всех игроков организатором заменён самостоятельной отметкой.
   Массовые административные действия могут быть полезны, но это отдельное решение.
4. Общий сохраняемый черновик заменён опубликованной открытой тренировкой.
   По последнему правилу R71 сначала сохраняется личный черновик, затем «Всё правильно» фиксирует участие; деньги меняются при завершении тренировки.
5. Макет второй версии содержит подтверждение завершения. Старое замечание
   про лишний переход нельзя использовать как основание убрать это подтверждение молча.
6. Ручная классификация посещаемости и имя в группе последним решением отложены
   на уровне интерфейса. Отсутствие их экранов сейчас не скрытая регрессия.

## Предлагаемый порядок следующей работы

### Сначала: участие без неожиданных изменений

Проверить установленные исправления на клиенте. Вместо разделения входов пользователь затем выбрал единую явную кнопку «Играл» (R63).
Проверить повторное нажатие без сброса значений и сохранение всей правки только по «Всё правильно».
Вернуть прямые административные действия в личную панель, как в макете.

### Затем: обзор состава и короткая навигация

Показать в списке участие, время, оплату и +1. Подключить «Играли раньше / Все участники»,
различать одинаковые имена и сохранять страницу возврата. Свернуть главное меню
до согласованной структуры. Ручные `is_attending` и `nickname` оставить отдельным
следующим этапом, как договорились.

### После этого: история и стоимость обработки

Сделать краткую историю результата, сохранить подробный аудит вторым уровнем.
Вернуть подготовленный порядок посещаемости и пакетную запись кнопок.
До оптимизации зафиксировать количество запросов и транзакций на создание,
присоединение, +50 ₽, смену страницы и завершение. Лимит времени ответа измерять,
а не выводить из числа операций.

Эта очередь — предложение для обсуждения, не разрешение автоматически внедрить
все изменения. Перед следующим пакетом нужны конкретные обновлённые экраны.

## Как тестировать интеграцию и не терять замечания

### Что есть сейчас

- `AccountingTest`: расчётное ядро, округление, большие числа, сохранение сумм.
- `SettlementServiceTest`: настоящая SQLite и предметные операции.
- `SelfServiceBotTest`: обработчики и SQLite, но Telegram заменён подставным адаптером.
- `HttpTelegramApiTest`: настоящий HTTP-клиент и локальный сервер, проверяющий формат.

Это полезные проверки, но два последних уровня разъединены. Подставной адаптер
не моделирует всю ленту клиента. Проверка существования клавиатуры в объекте
не доказывает, что её видит человек после следующего обновления карточки.

### 1. Весь бот через HTTP — на каждую сборку

Запускать реальные обработчики, `HttpTelegramApi` и временную SQLite вместе.
Локальный сервер реализует используемые методы Telegram и хранит историю чатов,
сообщения с получателем, кнопки, входящие события и результаты доставки.
Входы подаются как реальные JSON-обновления, кнопки выбираются из ответа бота,
затем проверяются и итоговая лента, и база.

В модели истории учитывать сообщения пользователя и бота в одном порядке:
после ввода нового текста ID свежего ответа должен быть больше ID входящего
сообщения в том же чате. После callback-нажатия должен измениться текущий ответ,
а не появиться новый. Задержки, повторы, 429, отказ отправки и потеря ответа
после успешного приёма задаются управляемо, без настоящих ожиданий по минуте.

В этой модели следует проверять используемые правила API. Воспроизводить
неподтверждённые особенности отображения Telegram и выдавать модель за реальный
клиент нельзя.

### 2. Настоящий Telegram — перед выпуском

Отдельный тестовый бот, отдельная база и две закрытые тестовые группы.
Два пользовательских аккаунта позволяют поменять роли местами между группами.
Автоматический пользовательский клиент нажимает кнопки и получает обновления;
самого токена бота для имитации обычного участника недостаточно.
Telegram предоставляет [метод нажатия callback-кнопки только для пользователей](https://core.telegram.org/method/messages.getBotCallbackAnswer).

Для такого окружения потребуются пользовательская авторизация и отдельные
секреты тестового клиента; их не хранить в репозитории. Первое окружение можно
запускать локально, не добавляя нагрузку на небольшой рабочий сервер.
Тестовые группы и аккаунты в рамках этого ревью не создавались.

### 3. Настоящий интерфейс — короткий обязательный прогон

Автоматизация Telegram Web может проверять порядок сообщений, наличие видимых
кнопок после обновления и переходы. На клиенте, которым пользуется группа,
дополнительно пройти короткий сценарий: временные панели могут различаться
по поведению между клиентами. [Telegram описывает ограничения их доставки](https://core.telegram.org/bots/api#ephemeralmessagesandcommands).

Проверка API не заменяет этот шаг. Первоначально он может быть ручным,
с зафиксированными результатами, вместо отсутствующей проверки под видом автоматической.

### Минимальные сквозные сценарии

| Сценарий | Проверяемое поведение | Замечания |
| --- | --- | --- |
| Текст → ответ → кнопка → текст | Ответ ниже ввода, кнопка обновляет его, повтор события не создаёт копию | R36, R59 |
| Присоединиться → обновить общую карточку → +50 ₽ → выйти | Личные кнопки остаются видны; другие люди не видят чужую панель; оплата снимается только после подтверждения | R01, R37, R50, R63 |
| «Играл» → поправить данные → повторно «Играл» | Время и сумма не сбрасываются | R62–R63 |
| Оплатил → «Не играл» → подтверждение | Сумма не удаляется до подтверждения; изменившуюся сумму нельзя снять старым подтверждением | R63 |
| Две группы, один человек с разными ролями | Разные составы и балансы; администраторство не переносится | R25–R31 |
| 27 человек, последняя страница, длинные одинаковые имена | Все доступны, различимы, время и +1 видны, возврат на нужную страницу | R16, R20, R44 |
| 350 ₽ + 400 ₽, четверо, разное время и +1 | Верный итог, округление и отсутствие отдельного долга гостя | R01–R07, R14 |
| Завершить → перевод → возобновить → поправить → завершить | Старые долги сохраняются до завершения, реальный перевод не переписывается | R45–R46 |
| Перевод → уточнение → подтверждение другим человеком | Неправильный автор отклонён, повтор не удваивает деньги | R08–R11 |
| Перезапуск и потерянный ответ Telegram | Нет дублей финансов и автоматического размножения общей карточки | R47, R56–R57 |
| Старый закреп и заменённая личная панель | Закреп работает, заменённые кнопки прекращают работу после задержки | R56–R57 |

Для каждого R-пункта хранить ссылку на проверку либо пометку «ручная проверка»
или «ожидает реализации». При рефакторинге сценарий остаётся; изменяется его
подключение к новому коду. Удалять сценарий можно при явной смене требования,
которая отражена в этой таблице. Количество прошедших тестов не заменяет это соответствие.

## Остальные темы раннего обсуждения

Это вопросы настройки и эксплуатации, а не новые требования к экранам:

- Выбор Kotlin вместо Go/Python и настройка сборки: Kotlin, Java 21 и Gradle сохранены.
- SQLite вместо PostgreSQL: остаётся один файл, новое описание и запросы подготовлены.
- Исходники и общая документация хранятся в Git; настройки конкретной установки — отдельно.
- Локальный запуск, токен, имена бота и BotFather: это настройка конкретного бота, не основание менять имя при рефакторинге.
- Адрес сервера и параметры SSH хранятся в закрытых эксплуатационных заметках.
- «Почему передаём сборку, а не через GitHub»: исходники отправляются в GitHub, готовая сборка устанавливается отдельно. Автоматического развёртывания из GitHub нет.
- Память VDS, VMware и ballooning: прежний [разбор памяти](MEMORY_ANALYSIS.md) остаётся отдельной темой; новый код сам по себе не решает давление памяти гипервизора.
- Частичные права бота: Telegram-права нужны для взаимодействия с группой и проверки членства; роли администраторов нашего приложения — отдельный механизм.
- Ранние «пока под вопросом», «пока только по запросу» без исходных вопросов нельзя надёжно превратить в дополнительные функции. Автоматические напоминания и списание мелких долгов не считать согласованными по таким фрагментам.
