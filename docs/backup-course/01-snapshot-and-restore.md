# Лабораторная 1. Снимок и восстановление

Результат: увидеть своими глазами, что отдельный снимок сохраняет прежнее
состояние, даже когда исходные данные уже изменились. На этом этапе разбираемся
с данными и проверкой; облако и расписание появятся позже.

Два термина: **snapshot** — снимок состояния данных, **restore** — восстановление
из этого снимка. Создать снимок и доказать возможность восстановления — разные действия.

Нужны терминал в корне проекта, Java 21 и команда `sqlite3`. Все команды ниже
выполняются в одном терминале: переменная `lab_dir` хранит путь учебной папки.
Используются только искусственные данные. Команда `bot` не запускается, токен
и работающий сервер для этой лаборатории не нужны.

## 1. Подготовить отдельное место

```sh
lab_dir=$(mktemp -d /tmp/tennis-backup-lab.XXXXXX)
```

`mktemp -d` создаёт новую папку с уникальным именем. `lab_dir` — переменная
оболочки. Далее `$lab_dir` подставляет этот путь в команды. Мы явно используем
временную папку /tmp с именем без пробелов. Это учебное место: для настоящего
резервирования оно не годится.

Проверить инструменты:

```sh
./scripts/gradle.sh --version
sqlite3 --version
```

Если команда завершилась ошибкой, сначала разберём её. Не нужно менять рабочую
базу или установку сервера, чтобы исправить локальное учебное окружение.

## 2. Создать учебную базу приложения

```sh
./scripts/gradle.sh run --args="demo $lab_dir/source.sqlite" --console=plain
```

`run` запускает консольную программу проекта. `demo` создаёт новую искусственную
базу: одна тренировка «Теннис», четыре участника, оплаты стола 350 и 400 ₽,
завершённый расчёт. При существующем файле команда откажется его перезаписывать.

В выводе будут суммы участников и сообщение о целостности базы. Сообщения Gradle
про сборку относятся к запуску программы, а не к содержимому резервной копии.

Посмотреть исходные данные SQL-запросом только для чтения:

```sh
sqlite3 "$lab_dir/source.sqlite" "PRAGMA query_only=ON; SELECT title, status FROM trainings;"
```

`PRAGMA query_only=ON` запрещает этому соединению изменять данные SQL-командами.
SQLite при открытии может создавать служебные WAL/SHM-файлы; это отличается от
запрета любых записей в файловую систему. Такой запуск работает и со свежей базой
в режиме WAL в проверенном локальном окружении.

Ожидаем `Теннис|CLOSED`. Здесь `CLOSED` — значение статуса в базе, в карточке
бота оно отображается как «Учтена».

## 3. Сделать снимок

```sh
./scripts/gradle.sh run --args="backup $lab_dir/source.sqlite $lab_dir/snapshot.sqlite" --console=plain
```

Первый путь — источник, второй — новый файл копии. Программа открывает источник
только для чтения и вызывает SQLite Online Backup API. Это согласованный снимок
базы, а не последовательное копирование произвольных файлов с диска.
Копия проверяется до появления под окончательным именем. [Как работает API](https://sqlite.org/backup.html).

Пока база меняется, SQLite может держать подтверждённые записи в соседнем файле
`-wal`. Почему один `cp source.sqlite ...` для живой базы ненадёжен, подробно
проверим в следующей лаборатории. Сейчас эту задачу за нас решает Backup API.

## 4. Проверить содержимое копии

```sh
./scripts/gradle.sh run --args="verify $lab_dir/snapshot.sqlite" --console=plain
```

`verify` проверяет структуру SQLite, внешние ключи и финансовые инварианты:
сумма проводок одной операции равна нулю, балансы групп согласованы.
Это важная проверка, но она не знает, верно ли человек назвал тренировку.

```sh
sqlite3 "$lab_dir/snapshot.sqlite" "PRAGMA query_only=ON; SELECT title FROM trainings; SELECT COUNT(*) FROM training_players; SELECT SUM(paid) FROM training_players;"
```

Ожидаем три строки: `Теннис`, `4`, `750`. Это уже проверка конкретных ожидаемых
данных, а не только отсутствия повреждений файла.

## 5. Намеренно изменить только учебный исходник

Перед запуском попробуй предсказать: какое название будет в источнике,
а какое — в снимке после этой команды?

```sh
sqlite3 "$lab_dir/source.sqlite" "UPDATE trainings SET title='Ошибочное название' WHERE id='training';"
```

Команда меняет одну тренировку в искусственной базе этой лаборатории. Путь
не относится к рабочей базе бота. В отличие от предыдущих запросов здесь
намеренно нет `PRAGMA query_only=ON`, потому что мы моделируем ошибочное изменение.

```sh
sqlite3 "$lab_dir/source.sqlite" "PRAGMA query_only=ON; SELECT title FROM trainings;"
sqlite3 "$lab_dir/snapshot.sqlite" "PRAGMA query_only=ON; SELECT title FROM trainings;"
```

Источник покажет `Ошибочное название`, снимок — `Теннис`. Снимок не синхронизируется
с источником: именно поэтому он полезен для возврата к прежнему состоянию.

Можно повторить `verify` для источника. Он пройдёт: неверное название не нарушает
структуру SQLite и суммы расчётов. «Файл исправен» и «данные правильные» — разные проверки.

## 6. Восстановить в отдельную папку

```sh
mkdir "$lab_dir/restored"
cp "$lab_dir/snapshot.sqlite" "$lab_dir/restored/database.sqlite"
./scripts/gradle.sh run --args="verify $lab_dir/restored/database.sqlite" --console=plain
sqlite3 "$lab_dir/restored/database.sqlite" "PRAGMA query_only=ON; SELECT title FROM trainings; SELECT COUNT(*) FROM training_players; SELECT SUM(paid) FROM training_players;"
```

Здесь `cp` допустим: копируем уже готовый самостоятельный снимок, который никто
не изменяет. Проверка работает с отдельным восстановленным экземпляром, а не
подменяет изменённый источник.

Восстановленные данные: `Теннис`, `4`, `750`. Для первого урока это доказательство
восстановления содержимого. Полный запуск приложения в аварийном окружении,
совместимость версий и доступ к Telegram проверим на заключительном этапе.

## Что записать после выполнения

- Какие названия оказались в источнике, снимке и восстановленной базе.
- Что проверил `verify` и почему ошибочное название не вызвало отказа.
- Где находятся файлы и почему эта локальная практика ещё не защищает от потери компьютера.

Вопрос для обсуждения: если после снимка записать ещё один настоящий перевод,
появится ли он при восстановлении из этого снимка — и что это означает для ночного расписания?

Остановиться можно здесь. Следующий этап — наглядный опыт с WAL; restic,
облако и рабочее расписание пока не устанавливаем.
