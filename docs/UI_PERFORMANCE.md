# Задержки интерфейса: проверка и локальное улучшение

Разделять три составляющие: работу приложения и SQLite, обращения к Telegram,
ожидание процессора / памяти / диска на сервере. Маленькая база сама по себе
не гарантирует быстрый ответ, если страницы процесса постоянно читаются из swap.

## Что изменено

При отрисовке карточки имена уже загруженных аккаунтов повторно использовались
через отдельные чтения базы для каждой строки. Теперь они запоминаются в пределах
одной отрисовки и используются также для гостевых мест. Это не кеш разрешений:
права остаются актуальными для каждого обрабатываемого события.

Вход в обычное меню больше не проверяет права публикации самого бота для каждой
группы. Такая проверка нужна на выборе группы для создания и перед публикацией.
Членство текущего пользователя по-прежнему проверяется.

## Измерение на искусственных данных

Изолированная SQLite, 40 аккаунтов, 10 игроков, одна общая карточка и десять
открытых персональных панелей. Вместо Telegram — FakeTelegramApi; счётчики
транзакций Database и вызовов TelegramApi. Java 21, одна прогретая последовательность.

| Действие | Чтений до → после | Записей до → после | Локальное время до → после |
|---|---:|---:|---:|
| Личное меню | 13 → 13 | 13 → 13 | 19 → 19 мс |
| Нажатие времени: собственный ответ | 23 → 12 | 12 → 12 | 19 → 18 мс |
| Общая карточка и десять панелей | 173 → 52 | 57 → 57 | 91 → 73 мс |
| Нажатие вместе с обновлением карточек | 196 → 64 | 69 → 69 | 105 → 86 мс |

В личном меню запросов членства стало два → один для выбранного примера.
Обновление общей карточки и десяти панелей по-прежнему делает 21 обращение:
один вызов общей карточки, десять проверок членства и десять обновлений панелей.
Это сохраняет защиту от доступа после выхода из группы.

Число чтений в полном сценарии уменьшилось примерно на 67%. Время приведено как
иллюстрация одного локального измерения, без сети; это не скорость рабочего бота
и не оценка процента ускорения на сервере.

## Что ещё проверять на сервере

- `free`, `/proc/pressure/memory`, `/proc/pressure/io`, активность swap;
- память и swap контейнера, лимит и счётчики OOM, перезапуски;
- загрузку CPU и доступную память виртуалки, включая ballooning гипервизора;
- несколько последовательных HTTPS-запросов Telegram с повторным соединением:
  первый запрос включает установку TLS, последующие показывают обычную задержку;
- размер SQLite / WAL и длительность чтения небольшой выборки;
- время обработки событий отдельно от фонового обновления карточек.

Чтение метрик не требует изменения системных параметров. Рабочие адреса, показатели,
состав служб и подробные результаты хранятся в закрытых заметках вне Git.

Обновление карточек выполняется последовательно. Если открыто много панелей,
их сетевые запросы могут задержать следующий цикл получения событий. Это возможный
остаточный источник задержки; параллельная обработка в этом выпуске не добавлялась.
Нельзя считать причину каждого медленного нажатия доказанной без измерения полного
пути реального события. Увеличение лимита контейнера не устраняет нехватку памяти
на самом хосте, если контейнер ещё не достиг своего лимита.
