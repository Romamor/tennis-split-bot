# Новая модель данных

Статус: реализация после утверждения основного интерфейса. Новая база создаётся отдельно; старая тестовая база остаётся архивом. Прежние форматы команд, псевдопользователи и JSON-снимок финансового состояния не переносятся в новый код.

Подробное описание полей и связей: [DATABASE_V2_TABLES.md](DATABASE_V2_TABLES.md).

## Сущности: 13 таблиц

| Таблица | Содержимое |
| --- | --- |
| users | Telegram ID, актуальные имя и username; аккаунт бота помечен отдельно |
| groups | Telegram chat ID, название, часовой пояс |
| group_users | Известные боту аккаунты в контексте группы; связь сохраняется после выхода ради расчётов. Ручной признак «ходит / не ходит» и имя в группе заложены в схему для будущей функциональности |
| group_admins | Только назначенные администраторы бота и автор назначения; суперадминистраторы определяются через Telegram при запросе |
| trainings | Название, дата и начало, состояние, текущая версия и номер учтённой редакции |
| training_players | Одна строка на аккаунт в тренировке: участие, время, оплата, гостевое время, порядок округления |
| transfers | Состояние реального перевода, стороны, сумма, дата, автор и инициатор уточнения |
| actions | Один журнал действий с исходной командой, автором, изменением и результатом; одновременно защита от повторов и очередь обновления карточек |
| balance_entries | Денежное влияние действия на аккаунты группы; из этих записей получается текущий баланс |
| bot_events | Входящие события Telegram, зафиксированный план и завершение обработки |
| bot_sessions | Текущий экран и ожидаемый ввод пользователя в конкретном чате |
| bot_buttons | Постоянные ссылки и кнопки с владельцем/областью действия и жизненным циклом |
| bot_deliveries | Результаты отправок, номера общих и личных сообщений, неизвестные результаты |

## Основные ограничения

- Пользователь идентифицируется только числовым Telegram ID; username не задаёт личность и может изменяться.
- Связи тренировок, переводов, аккаунтов и финансовых записей включают group_id. Внешние ключи запрещают перепутать записи разных групп.
- Самостоятельно можно менять только свою строку участия в открытой тренировке или уточнении. Администратор меняет любую строку. Администраторы Telegram автоматически имеют старшие права в своей группе; назначенный администратор не делегирует роль.
- Нахождение в группе не означает участие в тренировке. При присоединении — 0 ч и 0 ₽; повторное присоединение не сбрасывает поправки.
- По задачам #1 и #2 выход из участия сохраняет оплату. Можно добавить несколько гостей с временем пригласившего; отдельных аккаунтов для них нет.
- Суммы — целые рубли. Финансовая операция сбалансирована; переполнение и частичное применение исключаются транзакцией и расчётным ядром.

## Источник истины для денег

Текущий финансовый результат хранится только в balance_entries. Нет отдельного JSON-снимка балансов, всех тренировок и переводов.

При первом завершении добавляется рассчитанное влияние тренировки. При возобновлении проводки не меняются. При повторном завершении в одной транзакции снимается прежнее влияние именно этой тренировки и добавляется новое. Проводки реальных переводов независимы. Отмена снимает влияние тренировки, а не удаляет её историю.

RestoreTraining переводит отменённую тренировку в OPEN, сохраняя ту же строку,
состав и введённые суммы. Добавляется запись истории без проводок; applied_version
остаётся 0. Повторный учёт через FinishTraining применяет расчёт ровно один раз.
Восстановление доступно администратору соответствующей группы и проверяет версию записи.

Текущий состав нормализован в training_players. JSON допустим для неизменяемой истории до/после и для временных диалогов; из него не читаются текущие балансы или рабочий состав.

## Повторы и конкурентные изменения

Повтор одного Telegram update_id использует ту же команду и результат. Два разных нажатия +100 ₽ — два намеренных увеличения суммы; повтор доставки одного нажатия ничего не добавляет. Одновременные поправки разных людей не конфликтуют по общей версии состава. Завершение проверяет версию всей тренировки, показанную администратору на подтверждении.

## Разделение интерфейса и доставки

Одна финансовая запись может породить несколько уведомлений. Поэтому журнал действий и доставка остаются раздельными. Отдельные workflow_commands, operations, outbox и tg_updates/tg_plans больше не нужны: их обязанности объединены соответственно в actions и bot_events.

В пользовательской панели ChangeAttendance немедленно обновляет training_players,
версию и actions. Это ещё не проводки: они применяются при учёте тренировки.
В личной форме администратора остаётся черновик в bot_sessions.input_json и
подтверждение SaveAttendance с проверкой исходной строки, защищающей от чужих правок.
bot_sessions.panel_json хранит экран открытой персональной панели для фонового
обновления. Содержимое таблицы не сохраняется в нём повторно.
bot_deliveries хранит pin_status для закрепления; прежнее поле display_page больше не используется,
успешное или неизвестное закрепление не повторяется автоматически.

Версия схемы 3 мигрирует версии 1 и 2 транзакционно. Состав, историческое гостевое
время и проводки сохраняются; следующий ввод участия синхронизирует гостевое время
с временем пригласившего. Восстановление старой копии отдельно проверяют через verify.

Кнопки групповых карточек не принадлежат одному человеку: автор нажатия проверяется при обработке. Персональные кнопки принадлежат конкретному пользователю и экрану. Актуальные кнопки защищены; заменённые очищаются через 2 минуты, постоянные ссылки — бессрочные.

## Проверки до установки

Изоляция групп и прав; конкурентные поправки; повтор нажатия и повтор доставки; 300 ₽ и шаги; гости; плательщик без участия; первое и повторное завершение; отмена; аванс и частичный возврат; уточнение перевода; сохранность балансов при возобновлении; нулевые балансы только у игравших; пагинация; ошибки отправки и восстановление карточки.

## Ручные настройки группы

`group_users.is_attending` и `group_users.nickname` предусмотрены в SQL-схеме.
Обновление аккаунта и членства сохраняет их. Управление ими и использование
в интерфейсе — будущая функциональность, явно отмеченная в README.
