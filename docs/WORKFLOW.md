# Участники, права и совместные черновики

Прикладной слой находится в `application/GroupService.kt`. Интерфейс — команды `WorkflowCommand` и методы чтения. Telegram-адаптер и экраны реализованы поверх него; живой запуск ещё не выполнен. Инструкция находится в `docs/TELEGRAM.md`.

## Кто может действовать

На вход передаётся `VerifiedGroupMember`: группа, Telegram user ID и подтверждённый признак администратора. Адаптер проверяет реального отправителя и членство через API. Прикладная библиотека сама не делает сетевой запрос и не проверяет достоверность произвольно созданного объекта. Локальная демонстрация использует явно вымышленные подтверждения.

Группу создаёт подтверждённый администратор; он становится организатором. Признак администратора Telegram не повышает права автоматически в уже созданной группе. Организатор может назначить другого организатора из привязанных участников.

| Действие | Правило |
| --- | --- |
| Просмотреть участников, историю и черновики | Текущий проверенный участник чата |
| Добавить человека по имени | Любой участник |
| Связать себя с записью | Только незанятая запись; у пользователя максимум одна запись в группе |
| Исправить привязку, отметить «Больше не ходит» | Организатор |
| Переименовать запись | Сам участник или организатор |
| Создать или редактировать общую тренировку | Любой участник |
| Впервые учесть тренировку, отменить её или отбросить общие рабочие правки | Создатель или организатор |
| Сохранить исправления уже учтённой тренировки | Любой подтверждённый участник её группы, даже если не играл |
| Записать перевод | Отправитель, получатель либо разрешённый представитель |
| Снять уточнение перевода | Тот, кто начал уточнение |

Представительство указывается явно через `onBehalfOf`. Организатор может действовать за непривязанную запись. Для привязанного человека, вышедшего из чата, адаптер должен отдельно передать проверенное подтверждение `VerifiedAbsentMember` для той же группы и того же пользователя. Отметка «Больше не ходит» сама по себе не является подтверждением выхода из чата.

Если организатор начал уточнение от имени непривязанного участника, а тот затем привязал Telegram, этот же организатор может завершить начатое уточнение. Это не даёт права начинать новые операции от имени присутствующего привязанного участника.

## Участники и гости

Постоянный `participant_id` не меняется при переименовании, привязке, исправлении связи или деактивации. Все изменения видны в истории с автором, прежним и новым значением. Одинаковые имена разрешены, но идентификаторы и привязки различаются.

Неактивные участники скрыты из списка по умолчанию. Вызов `participants(..., includeInactive = true)` возвращает их вместе с балансами; `settlementPlan()` всегда учитывает все финансовые остатки. Право читать данные зависит от текущего членства в чате, а не от посещения тренировок.

«+1» — дополнительная строка времени в черновике с идентификатором пригласившего. `DraftContent.withPlusOne()` подставляет его время при добавлении; затем время гостя можно исправить отдельно. У гостя нет собственного профиля или баланса. Новая тренировка начинается пустой, без переноса гостей предыдущей встречи.

## Жизненный цикл тренировки

| Состояние | Значение |
| --- | --- |
| `DRAFT` | Неучтённая рабочая запись; состав и оплаты могут быть неполными |
| `POSTED` | Сохранённый вариант учтён в балансах |
| `EDITING` | Есть общие правки, но в балансах действует последний учтённый вариант |
| `CANCELLED` | Тренировка отменена, история сохранена |

`CreateDraft` создаёт пустой черновик. `SaveDraft` заменяет рабочее содержимое только при совпадении версии. Если тренировка уже учтена, сохранение правок переводит её в `EDITING` без изменения денег. `PostDraft` учитывает рабочий вариант и заменяет прежнее финансовое влияние в той же транзакции. `DiscardChanges` возвращает опубликованный вариант, а `CancelDraft` снимает влияние тренировки, сохраняя реальные переводы.

Версия рабочей записи и версия финансового расчёта различаются. Просмотр черновика не увеличивает ни одну из них. Старый экран получает ошибку устаревшей версии, а не перезаписывает чужую правку. Обычный выход из будущего диалога не должен вызывать `CancelDraft` или удалять общую запись.

В черновике можно ещё не указать игроков или оплаты, но уже введённые значения проверяются: положительные минуты и суммы, одна оплата на плательщика, отсутствие дубликатов игроков и существование всех записей в этой группе. На этапе учёта требуется полный корректный расчёт. Будущую дату можно сохранить в черновике; учесть её можно только после наступления даты в часовом поясе группы.

Порядок уже присутствующих игроков сохраняется при редактировании, даже если клиент прислал список в другом порядке. Новые строки добавляются в конец. Это сохраняет правило распределения лишних рублей между одинаковыми долями.

## Повторы и похожие переводы

Каждое действие получает постоянный идентификатор команды. Повтор с тем же автором и содержимым возвращает прежний результат, включая после перезапуска. Изменение содержимого или автора с прежним идентификатором отклоняется.

Отдельно проверяются независимо записанные переводы с одинаковыми сторонами, суммой и датой. Выбрасывается `SimilarTransferFound` со списком записей. Будущий интерфейс должен показать их и предложить «Это ещё один перевод». Только после такого подтверждения команда отправляется с `allowSimilar = true`. Отменённые ошибочные переводы не мешают записать новый реальный перевод.

## Атомарность и история

Права и версии читаются внутри транзакции записи. Сохранение черновика, финансового события, аудита и результатов команд выполняется той же транзакцией. Ошибка на последнем шаге не оставляет учтённой тренировки с прежним черновиком или нового баланса без истории.

В `workflow_audit` остаются организационные действия и изменения привязок. Финансовые операции дополнительно сохраняются в прежнем журнале и очереди событий. Просмотр и правки черновика не создают финансовых событий для общей карточки, пока тренировка не учтена.

```sh
./scripts/gradle.sh run --args="workflow-demo data/workflow-demo.sqlite"
./scripts/gradle.sh test
```

В демонстрации 14 действий и три финансовые операции. Итоговые балансы: Андрей +175 ₽, Борис −50 ₽, Саша −125 ₽. Саша связан с ранее созданной записью и отмечен как переставший ходить; его долг сохраняется. Повторный запуск не создаёт новых действий.

Добавлены 24 проверки прикладных сценариев и проверка миграции старой схемы до текущей с сохранением финансовой истории. Вместе с ядром, хранилищем и Telegram-адаптером проходят 95 тестов. Проверены конкурирующие привязки и правки, права, местная дата, сохранение баланса при привязке и деактивации, откат последнего шага записи и восстановление из копии.
