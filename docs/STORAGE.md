# Постоянное хранение

Хранилище находится в `SqliteAccountingStore`. Каждый вызов открывает соединение с файлом SQLite и закрывает его по завершении; постоянного процесса базы нет. Данные демонстрации хранятся в `data/demo.sqlite`, тесты используют собственные временные файлы JUnit.

## Что записывается

| Таблица | Данные |
| --- | --- |
| `group_state` | Текущие балансы, состояния тренировок и переводов, версия группы |
| `operations` | Уникальная команда, проверенный автор, представленная сторона, полные входные данные, дата и пояснение, результат и время записи |
| `balance_entries` | Изменения балансов от каждой операции в исходном порядке |
| `outbox` | Событие для будущего обработчика уведомлений и отметка об обработке |
| `app_groups`, `organizers` | Часовой пояс группы и назначенные организаторы |
| `participants` | Имена, постоянные идентификаторы, привязка Telegram ID, активность и версии |
| `training_drafts` | Общая рабочая копия, последняя опубликованная копия и обе версии |
| `workflow_audit`, `workflow_commands` | История организационных действий и результаты команд |
| `tg_*` | Аккаунт бота, группы, диалоги, ссылки, кнопки, планы обновлений и результаты отправок |

Финансовые снимки и команды записываются в JSON с версией формата 1. Денежные значения остаются целыми `Long`; строки журнала используют SQLite `INTEGER`. Текущая схема имеет `user_version=6`. Старые версии последовательно получают таблицы из `002_workflow.sql`, `003_telegram.sql`, `004_editors.sql`, `005_button_lifecycle.sql` и `006_active_buttons.sql` в одной транзакции. Старые финансовые строки не меняются. Неизвестная версия или база другого приложения отклоняется. Открытие через `SqliteAccountingStore`, включая `verify`, выполняет миграцию при необходимости; для проверки старой резервной копии сначала сделайте её отдельную копию.

Снимок состояния нужен, чтобы не запускать старые команды повторно при каждом открытии базы. Поэтому изменения будущего алгоритма округления сами по себе не пересчитают прошлые тренировки. Полные исходные данные каждой команды остаются в истории.

Финансовые записи ссылаются на постоянные идентификаторы участников. Имена, привязки, роли и черновики сохраняются отдельно. Если прикладная группа инициализируется поверх старых финансовых данных, имеющиеся идентификаторы превращаются в непривязанные профили с именами по идентификаторам. Организатор может переименовать их; суммы и история сохраняются.

## Одна команда — одна транзакция

1. Начать `BEGIN IMMEDIATE`, получив право записи до чтения версии.
2. Найти прежнюю команду по группе и её идентификатору. Если автор, данные и пояснение совпадают, вернуть прежний результат. Изменённое содержимое с прежним идентификатором отклонить.
3. Прочитать сохранённое состояние группы и проверить его согласованность с активными источниками.
4. Выполнить финансовую команду через `AccountBook`.
5. Сохранить новое состояние, исходную команду, журнал и событие очереди.
6. Зафиксировать всё вместе. Любая ошибка до успешной фиксации откатывает всю операцию.

Используются `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=FULL` и режим WAL. Если блокировка не освобождается за время ожидания, вызывающий код получает ошибку; возможный повтор должен использовать тот же идентификатор команды. При неопределённом результате фиксации повтор с тем же идентификатором также безопасен.

Ограничения уникальности и блокировки действуют в самой базе. Проверена работа независимых соединений, включая одновременные повторы и конкурирующие исправления одной версии.

`AccountBook` остаётся независимым расчётным ядром. В хранилище он восстанавливается из снимка для одной команды, а защита от ранее записанных команд обеспечивается таблицей `operations`. Нельзя использовать один `AccountBook` в памяти как замену постоянному хранилищу рабочего бота.

`GroupService` использует ту же транзакцию для прав, изменения черновика, финансовой команды, истории действий и результата прикладной команды. Внутренний вызов `executeInTransaction` не открывает вторую транзакцию. Проверен сбой уже после финансовых изменений, при вставке результата прикладной команды: откатываются все затронутые таблицы.

## Уведомления

`pendingEvents()` возвращает сохранённые события учёта. `acknowledge()` отмечает событие после успешной обработки. Повторная отметка безвредна; повтор финансовой команды не создаёт второго события.

`TelegramDelivery` преобразует события в общие карточки и личные уведомления с проверкой доступа. Намерение новой отправки сохраняется до запроса API. Неопределённый результат приостанавливает повтор; организатор восстанавливает карточку через `/restore` или явно подтверждает её отсутствие. Изменение известного сообщения повторяется безопасно. Доставка и запись результата не являются общей транзакцией; финансовая операция при повторе не выполняется заново.

## Проверка и резервная копия

```sh
./scripts/gradle.sh run --args="verify data/demo.sqlite"
./scripts/gradle.sh run --args="backup data/demo.sqlite data/backups/demo-1.sqlite"
./scripts/gradle.sh run --args="verify data/backups/demo-1.sqlite"
```

Проверяются физическая целостность SQLite, внешние ключи, непрерывность журнала, совпадение его балансов с текущим состоянием и наличие события очереди для каждой операции. Это проверка согласованности, а не криптографическая защита от намеренного изменения всех согласованных данных.

Копия создаётся командой SQLite `VACUUM INTO`, которая включает согласованные данные работающей базы, в том числе зафиксированные изменения из WAL. Существующая копия не перезаписывается. Файл резервируется перед копированием; если операция прервалась, его наличие само по себе не означает успешную копию. Успешная команда заканчивается проверкой новой базы.

Восстановление: открыть проверенную копию как отдельную базу. Рабочий файл не заменяется автоматически. После появления постоянно работающего бота путь к базе будет задаваться его настройкой; перед переключением понадобится остановить запись старого процесса. Расписание копирования и хранение копий на другом диске или сервере ещё предстоит настроить при размещении бота.

## Проверки этапа

Интеграционные тесты работают с реальной SQLite: повторное открытие, полный финансовый сценарий, сохранение инициатора уточнения, исправления и отмены, конкурирующие соединения, повтор команды с изменёнными данными, переполнение и разделение групп.

Сбой воспроизводится триггером, который отклоняет вставку в `outbox` после записи нового состояния и журнала. Проверяется откат всех таблиц и успешный повтор той же команды после устранения ошибки. Резервная копия проверяется при активном читателе WAL, затем открывается независимо от исходной базы. Дополнительно обнаруживаются повреждённый JSON и расхождение журнала с текущими балансами.

Источники по выбранным механизмам: [транзакции SQLite](https://www.sqlite.org/lang_transaction.html), [параметры соединения](https://www.sqlite.org/pragma.html), [резервная копия через VACUUM INTO](https://www.sqlite.org/lang_vacuum.html), [драйвер Xerial](https://github.com/xerial/sqlite-jdbc).

## Личные формы (схема 4)

`tg_editors` хранит отдельный ввод пользователя: базовую версию общей тренировки,
текущий состав/оплаты и локальную версию. Каждое движение не меняет общий
черновик, аудит или деньги. Кнопки хранят ссылки на форму и намерение действия,
а вся клавиатура записывается одной транзакцией.

`CommitDraft` проверяет базовую версию и атомарно создаёт/сохраняет черновик,
при необходимости учитывает тренировку и записывает одно событие аудита.
Неудачный расчёт откатывает также создание новой общей тренировки.
Повторное нажатие использует сохранённое намерение и не повторяет расчёт.

Откат на старую программу со схемой 3 требует совместимой базы. Сначала
остановить запись и проверить новые операции; не подменять рабочую базу
старой копией, если после обновления появились пользовательские изменения.

## Срок жизни кнопок (схема 6)

В `tg_actions` хранятся `payload_hash`, `active` и `expires_at` (секунды UTC).
Одинаковое действие того же пользователя и группы использует прежний токен;
после совпадения хеша сравнивается полный JSON. Кнопки редактирования содержат
ожидаемую версию, переходы между экранами показывают свежие данные.

`active = 1` защищает кнопки актуального личного экрана без срока давности.
Перед запросом к Telegram новые кнопки также защищаются. После подтверждённого
обновления сообщения или отправки нового экрана только новый набор остаётся
активным; старый получает `expires_at = now + 120 секунд`. При неизвестном
результате запроса сохраняются оба набора. При окончательном отказе отправки
новые кандидаты снимаются с защиты, а прежние кнопки остаются доступными.
После следующего подтверждённого экрана неопределённость устраняется.

Метаданные принадлежат пользователю; смена группы в его личном диалоге заменяет
его текущий экран, не затрагивая экраны других пользователей. Сохранённый
`tg_sessions.panel_id` указывает на актуальное сообщение. При неудачной отправке
бот сохраняет прежний указатель. Подтверждение набора кнопок атомарно; сбой
между сетевым запросом и записью оставляет лишние защищённые кнопки, а не
удаляет потенциально видимый набор.

Очистка работает в цикле бота и перед событиями, с проверкой раз в 30 секунд.
За транзакцию удаляется до 1 000 неактивных просроченных записей. Полная порция
означает продолжение на следующем цикле. Дополнительно защищены токены
текущего `tg_sessions.input_json` и незавершённых `tg_plans`.

`create_draft`, `new_transfer`, запрос имени нового участника и `recover`
всегда получают новые идентификаторы. Повтор выполнения того же нажатия
сохраняет прежний смысл. Дата новой тренировки определяется при первом
нажатии, а не при давнем показе меню, и фиксируется в плане для повторов.

У закреплённого группового меню постоянные ссылки `tg_links`, которые не
очищаются. Планы обработки, завершённые события, личный ввод и финансовые
журналы также не удаляются. Освободившиеся страницы SQLite используются
повторно; принудительный `VACUUM` не выполняется.

Проект пока тестовый: при переходе на схему 6 старые неподтверждённые наборы
кнопок получают обычные 2 минуты, без сохранения совместимости с прежними
экранами. После установки нужно вызвать `/menu`. Это не сбрасывает данные
тренировок и расчётов. Специальное хранение старых меню ради совместимости
не реализовано по решению пользователя.
