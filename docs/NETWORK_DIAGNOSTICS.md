# Проверка новой площадки перед переносом

Работающий бот остаётся на исходном сервере, пока новая площадка не проходит
сетевую проверку. С одним рабочим токеном нельзя запускать два процесса получения
событий одновременно. Для переноса используем проверенный установленный выпуск,
а не незавершённые изменения в рабочем каталоге.

## Первый этап: исходящий доступ

Проверить SSH, доступные память и диск, DNS для `api.telegram.org`, затем HTTPS
к Telegram и контрольным адресам. Если контрольные адреса доступны, а Telegram нет,
это не общий отказ интернета. Совпадение DNS-ответа на двух серверах и успешное
подключение с одного из них сужают проблему до пути от другой машины.

Проверки выполнять без токена. HTTP-ответ, включая перенаправление, уже доказывает,
что TCP и TLS установились. Значение HTTP=000 вместе с нулевым временем соединения
и сообщением connect timeout означает, что соединение не установлено.

## Проверка сетевого экрана и заголовков пакетов

[diagnose-network.sh](../deploy/diagnose-network.sh) — диагностический сценарий.
После просмотра выполнить на целевой Linux-машине:

```sh
sudo sh diagnose-network.sh
```

Права администратора нужны для чтения правил фильтрации и захвата заголовков
пакетов. Сценарий не устанавливает пакеты, не меняет правила, не перезапускает
службы и не обращается к секретному файлу бота. Он создаёт закрытый временный
каталог отчёта и делает ограниченный запрос к публичному Telegram API.

В отчёте:

- `route.txt`: выбранный адрес и маршрут.
- `nft.txt`, `iptables.txt`: правила хоста, если команды доступны.
- `tcp.txt`: текстовая сводка заголовков TCP к выбранному адресу на порту 443,
  если доступен tcpdump; бинарный дамп и содержимое сообщений не сохраняются.
- `curl.txt`: результат запроса и время установления соединения.

Сценарий передаёт права на отчёт пользователю, вызвавшему sudo. Отчёт содержит
сетевые адреса и настройки; хранить его вне Git. Обычный запуск без root прекращается
до создания отчёта. Для работы нужны curl, getent и ip; захват ограничен 14 секундами.

Если видны исходящие SYN без входящих SYN-ACK, запросы дошли до наблюдаемого
интерфейса, но ответ туда не вернулся. Это ещё не доказывает виновность провайдера:
далее проверяются правила облака и внешний маршрут, при необходимости через поддержку.
Если пакеты не видны, сначала исключить ошибку захвата и локальную фильтрацию.
Нельзя менять правила Docker или открывать все порты на основании одного тайм-аута.

## Порядок переноса после исправления сети

1. Проверить API на новой площадке сначала с хоста, затем из контейнера.
2. Подготовить установленный выпуск, конфигурацию и секреты с закрытыми правами.
3. Проверить копию базы совместимой программой без запуска второго бота.
4. Остановить старый процесс и получить финальную согласованную копию базы.
5. Запустить ровно один процесс на новой площадке; проверить выпуск, целостность,
   обработку событий и доставку карточек. Оставить прежнюю площадку для возврата.
6. При возврате учесть данные, принятые на новой площадке: старый снимок нельзя
   безусловно подставить вместо новой базы и потерять пользовательские действия.

[Группы безопасности Yandex Cloud](https://yandex.cloud/ru/docs/vpc/concepts/security-groups)
действуют отдельно от сетевого экрана внутри виртуальной машины.
