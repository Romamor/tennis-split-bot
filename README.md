# Расчёты теннисной группы

Проект на **Kotlin/JVM**, сборка **Gradle Kotlin DSL**, среда **Java 21**. Требования и сценарии: [SPEC.md](SPEC.md).

Реализованы расчётное ядро, SQLite, участники, совместные черновики и Telegram-интерфейс. Бот проверяет членство, хранит диалоги и показывает одну общую карточку на тренировку. Бот @example_bot работает на VDS; изменения интерфейса проверяются локально и устанавливаются с резервной копией базы.

## Первый запуск Telegram

1. Создать бота через официальный [@BotFather](https://t.me/BotFather), команда `/newbot`.
2. Вставить токен в `TELEGRAM_BOT_TOKEN` в локальном `.env`. Файл подготовлен и исключён из контроля версий.
3. Запустить:

```sh
./scripts/gradle.sh run --args=bot
```

Затем открыть личную переписку с ботом, добавить его администратором группы и отправить `/setup` от своего имени администратора. Появившееся меню закрепляется вручную. Полная инструкция и восстановление карточек: [docs/TELEGRAM.md](docs/TELEGRAM.md).

## Быстрый запуск

Из папки проекта:

```sh
./scripts/gradle.sh test
```

Команда запускает тесты. На macOS скрипт ищет установленную Java 21, затем Java внутри IntelliJ IDEA. На этом компьютере используется `/Applications/IntelliJ IDEA.app/Contents/jbr/Contents/Home`. Настраивать глобальную Java или устанавливать Gradle отдельно не требуется. На других компьютерах нужна Java 21; можно указать её каталог через `JAVA_HOME`.

Первая сборка скачивает Gradle и зависимости Kotlin/JUnit, поэтому нужен интернет. Последующие сборки используют загруженные файлы. Кэш скрипта находится в `.gradle-user-home/` внутри проекта. Значение `GRADLE_USER_HOME`, если задано пользователем, сохраняется.

Посмотреть согласованный пример трёх тренировок:

```sh
./scripts/gradle.sh run
```

Собрать проект вместе с тестами и пакетом приложения:

```sh
./scripts/gradle.sh build
```

Отчёт тестов находится в `build/reports/tests/test/index.html`. Команда `run` без аргументов показывает демонстрацию в памяти процесса; она не обращается к Telegram или реальным данным группы.

## Проверить сохранение в базе

Записать тот же пример в отдельную демонстрационную базу:

```sh
./scripts/gradle.sh run --args="storage-demo data/demo.sqlite"
```

Первый запуск сохраняет семь операций. Повторный запуск использует существующий файл и сообщает «Новых операций: 0; всего: 7». Итог: Андрей +62 ₽, Борис +162 ₽, Вера −224 ₽, Саша 0 ₽. Это отдельная группа `demo` с искусственными данными, а не подключение вашей группы Telegram.

Проверить базу и создать резервную копию:

```sh
./scripts/gradle.sh run --args="verify data/demo.sqlite"
./scripts/gradle.sh run --args="backup data/demo.sqlite data/backups/demo-1.sqlite"
./scripts/gradle.sh run --args="verify data/backups/demo-1.sqlite"
```

Для новой копии нужно новое имя: существующий файл не перезаписывается. Команда резервного копирования создаёт согласованную копию средствами SQLite и проверяет её. При работе базы рядом могут существовать файлы `-wal` и `-shm`; для копирования работающей базы используйте команду `backup`, а не копирование одного основного файла. Подробности: [хранение и восстановление](docs/STORAGE.md).

## Участники и сохранение тренировок

Выбор игроков, времени и оплат изменяет личную форму. «Ещё → Сохранить на потом»
сохраняет одну общую редакцию без изменения долгов; «Записать тренировку»
одновременно сохраняет и применяет расчёт. Личная форма переживает перезапуск,
но не создаёт записи общего аудита при каждом нажатии. «Закрыть без сохранения»
удаляет только личный ввод. Чужую сохранённую редакцию нельзя молча затереть.

Активные участники и балансы показываются по посещаемости; неактивные доступны
отдельной кнопкой. Их долги сохраняются. Порядок кэшируется по версии данных
и фиксируется на время выбора игроков. +1 отображается в строке пригласившего.


```sh
./scripts/gradle.sh run --args="workflow-demo data/workflow-demo.sqlite"
```

Демонстрация создаёт участников, привязывает их к записям, добавляет «+1», учитывает тренировку и общие правки, записывает возврат и отмечает ушедшего участника. Итог: Андрей +175 ₽, Борис −50 ₽, Саша −125 ₽. В истории 14 действий и три финансовые операции; повторный запуск ничего не дублирует.

Проверка членства в этой локальной демонстрации подставляется явно. Запросов к Telegram нет. Прикладные правила и граница проверки личности описаны в [docs/WORKFLOW.md](docs/WORKFLOW.md).

## Таблицы базы данных

Используется один файл SQLite. Текущая версия схемы — **4**, в ней **21 таблица приложения**:
6 для групп и тренировок, 4 для денежных расчётов и 11 для работы Telegram.
Встроенная таблица SQLite `sqlite_sequence` обслуживает нумерацию журнала и в эти 21 не входит.
Это описание существующей реализации; предложения по упрощению — в [ревью базы](docs/DATABASE_REVIEW.md).

Рабочая база на сервере: `/opt/tennis-split-bot/data/bot.sqlite`.
Локальная база по умолчанию: `data/bot.sqlite`; путь можно изменить настройкой.
Для знакомства подготовлены [инструкция просмотра](docs/DATABASE_INSPECTION.md)
и [примеры запросов](docs/inspect.sql). Локальная копия из инструкции сделана
до схемы 4, поэтому в ней ещё нет `tg_editors`.

### Группы, участники и тренировки

| Таблица | Что хранит | Зачем нужна и что смотреть |
| --- | --- | --- |
| `app_groups` | Идентификатор расчётной группы, часовой пояс, создатель | Общие настройки. Название чата находится в `tg_groups`. |
| `organizers` | Пары `group_id` + `user_id` | Кто назначен организатором расчётов в конкретной группе. Это роль внутри бота, не копия списка администраторов Telegram. |
| `participants` | Имена игроков, активность, необязательная привязка к Telegram, версия записи | Основной список игроков. `active = 1` — ходит, `0` — не ходит. `telegram_user_id = NULL` — запись пока ни с кем не связана. |
| `training_drafts` | Дата, статус, автор, версии, состав с временем и оплаты | **Все сохранённые тренировки**, включая уже учтённые и отменённые, несмотря на слово `drafts` в названии. Состав и оплаты лежат в JSON. |
| `workflow_audit` | Автор, время, вид действия, состояние до и после | История изменений участников, тренировок и переводов. Выбор отдельных галочек в личном вводе сюда не попадает. |
| `workflow_commands` | Входная команда, её автор и сохранённый результат, ссылка на запись аудита | Защита от повторного выполнения: повтор одной команды возвращает прежний результат. Сейчас создаётся одна строка на каждую строку `workflow_audit`. |

У тренировки есть два содержимых:

- `content_json` — последняя **сохранённая общая** редакция: дата, `players` и `payments`.
- `published_json` — последняя редакция, которая была применена к балансам; до первого учёта — `NULL`.

В `players` указаны `participantId`, время `minutes` и признак `plusOne`.
Время хранится в минутах, хотя интерфейс показывает часы. Гость `+1` — ещё один
элемент с идентификатором пригласившего и `plusOne = true`; отдельного баланса
или отдельной записи в `participants` у него нет. В `payments` указаны
`participantId` и `amount` — сколько человек оплатил за стол, в целых рублях.

Статусы `training_drafts`: `DRAFT` — ещё не учтена; `POSTED` — учтена;
`EDITING` — сохранены изменения, но в балансах пока действует прежняя
`published_json`; `CANCELLED` — вклад тренировки отменён. Отмена не удаляет
её историю и не отменяет реальные переводы между людьми.

### Денежные расчёты

| Таблица | Что хранит | Зачем нужна и что смотреть |
| --- | --- | --- |
| `operations` | Финансовые операции: учёт и исправление тренировки, её отмена, перевод, уточнение перевода | Неизменяемый журнал денежных действий. Есть автор, номер `sequence`, исходная команда `command_json` и дополнительные сведения `details_json`. Запись перевода ищется здесь по виду операции; отдельной таблицы `transfers` сейчас нет. |
| `balance_entries` | Изменение баланса одного участника в рамках одной операции | Например, `+300` одному и `−300` другому. Сумма `amount` по группе и участнику даёт его текущий баланс. Плюс — ему должны, минус — должен он. Это изменения баланса, а не отдельные долговые расписки между парами людей. |
| `group_state` | Номер финансовой версии и `checkpoint_json` — снимок текущего состояния группы | Отсюда программа читает текущие балансы, состояния переводов и учтённое влияние тренировок. Снимок обновляется вместе с финансовым журналом. У группы без финансовых операций строки может ещё не быть. |
| `outbox` | Финансовые события и отметку об их обработке доставкой | Позволяет после сохранения расчёта отдельно обновить сообщение в группе или уведомить участников. `acknowledged_at = NULL` — событие ещё не обработано. Заполненное поле не гарантирует прочтения или доставки всех сообщений: результаты отправок находятся в `tg_deliveries`. |

Связь финансовых записей: `operations` → `balance_entries` и `outbox`
по паре **`group_id` + `sequence`**. `sequence` нумеруется отдельно внутри группы.
При исправлении тренировки новая операция снимает её старый вклад и добавляет
новый; уже записанные переводы продолжают действовать независимо.

### Служебные таблицы Telegram

Для обычного просмотра долгов эти таблицы, кроме `tg_groups`, чаще всего не нужны.

| Таблица | Что хранит | Зачем нужна |
| --- | --- | --- |
| `tg_identity` | Одну запись с идентификатором и именем пользователя самого бота | Защита от случайного запуска другого бота с этой базой. Токена здесь нет. |
| `tg_groups` | `group_id`, числовой `chat_id` Telegram и название группы `title` | Связывает расчётную группу с реальным чатом. С этой таблицы удобно начинать запросы. |
| `tg_users` | Идентификаторы и последние известные имена пользователей | Имена авторов действий. Это не перечень всех участников всех чатов. |
| `tg_sessions` | Последнюю выбранную группу пользователя, сообщение с меню и ожидаемый текстовый ответ | Контекст личного диалога. **Одна строка на пользователя**, а не на пару «пользователь + группа». Поэтому `/menu` продолжает последнюю выбранную группу. |
| `tg_editors` | Личный ввод конкретного пользователя для конкретной тренировки: содержимое, исходную версию, порядок игроков | Восстановление незавершённого ввода после перезапуска. Ещё не сохранённые общие тренировки могут существовать только здесь. Балансы эта таблица не меняет. |
| `tg_actions` | Случайный идентификатор кнопки, пользователя, группу и действие | Проверяет, кому и какой группе принадлежит нажатие. Новые наборы кнопок создают новые строки. |
| `tg_links` | Ссылки из общего чата на меню или тренировку в личной переписке | Ссылка сохраняет целевую группу. Доступ дополнительно проверяется при открытии. |
| `tg_updates` | Номер входящего события Telegram и признак завершённой обработки | Не даёт повторно обрабатывать уже завершённое событие; из неё определяется позиция дальнейшего чтения событий. |
| `tg_plans` | Выбранное действие для входящего события, включая зафиксированную команду сохранения | Позволяет продолжить прерванную обработку с теми же данными, даже если пользователь уже изменил ввод. |
| `tg_deliveries` | Ключ отправки, чат, номер сообщения и статус доставки | Помнит созданные сообщения и результат отправки. `SENT` — отправлено, `UNKNOWN` — результат неизвестен, `FAILED`/`BLOCKED` — проблема доставки, `RETRY` — можно повторить позднее, `SENDING` — отправка начата. |
| `tg_recoveries` | Идентификатор команды восстановления сообщения и ключ отправки | Не даёт повторному нажатию восстановления заново сбросить уже восстановленное сообщение. Обычно строк мало или нет. |

Старые `tg_actions`, `tg_plans` и `tg_updates` сейчас автоматически не очищаются.
Это известное место для упрощения; финансовую историю не следует путать с
временным состоянием кнопок и диалогов.

### Как данные разделены между группами

Участники, тренировки, операции и балансы связаны с **`group_id`**.
Одинаковый `participant_id` или `draft_id` в двух группах означает разные записи.
В запросах и соединениях таблиц нужно учитывать группу вместе с идентификатором
участника или тренировки. Привязка одного Telegram-пользователя также отдельна
для каждой группы; глобальными остаются его имя и текущая сессия личного диалога.

Например, сначала найти группу:

```sql
SELECT group_id, title FROM tg_groups;
```

Затем подставить её `group_id` вместо `нужная-группа`:

```sql
SELECT p.display_name,
       p.active,
       COALESCE(SUM(e.amount), 0) AS balance_rub
FROM participants AS p
LEFT JOIN balance_entries AS e
  ON e.group_id = p.group_id
 AND e.participant_id = p.participant_id
WHERE p.group_id = 'нужная-группа'
GROUP BY p.group_id, p.participant_id, p.display_name, p.active
ORDER BY p.display_name;
```

Отдельной таблицы «кто кому должен» нет: предлагаемые переводы вычисляются
из текущих балансов. Для просмотра и собственных запросов используйте копию
в режиме только чтения: прямая правка одной таблицы обойдёт проверки приложения
и не обновит связанные версии, журнал и финансовое состояние.

## Код и границы ответственности

- `src/main/kotlin/ru/movereon/tennis/core/Accounting.kt` — распределение расходов, проверка сумм, применение сбалансированных изменений и предложения переводов. Умножение при делении выполняется через `BigInteger`, а денежные суммы хранятся в `Long` в рублях.
- `src/main/kotlin/ru/movereon/tennis/core/AccountBook.kt` — журнал одной группы в памяти, версии, повторные команды и состояния переводов. Операции синхронизированы; неуспешное действие не меняет состояние. Хранилище использует это ядро для выполнения команд над восстановленным состоянием.
- `src/main/kotlin/ru/movereon/tennis/storage/SqliteAccountingStore.kt` — транзакции, восстановление состояния, журнал, очередь событий, проверка целостности и резервное копирование.
- `src/main/kotlin/ru/movereon/tennis/storage/StorageCodec.kt` — формат хранения исходных команд, дат, пояснений и снимков состояния; сериализация изолирована от расчётного ядра.
- `src/main/resources/db/001_accounting.sql` — первая версия схемы SQLite.
- `src/main/resources/db/002_workflow.sql` — группы, организаторы, участники, черновики и история действий.
- `src/main/resources/db/004_editors.sql` — личные формы и индекс версии сортировки.
- `src/main/resources/db/003_telegram.sql` — группы Telegram, диалоги, ссылки, кнопки, обновления и результаты отправок.
- `src/main/kotlin/ru/movereon/tennis/telegram/` — клиент API, проверка членства, экраны, доставка и запуск бота.
- `src/main/kotlin/ru/movereon/tennis/application/GroupService.kt` — проверка прав, привязка записей, совместные правки и атомарный учёт тренировки.
- `src/main/kotlin/ru/movereon/tennis/Demo.kt` — пример из спецификации.
- `src/test/kotlin/ru/movereon/tennis/core/` — точные сценарии, проверки ошибок, одновременных повторов и 1000 воспроизводимых сгенерированных случаев распределения.
- `src/test/kotlin/ru/movereon/tennis/storage/` — 17 интеграционных тестов реальной SQLite.
- `src/test/kotlin/ru/movereon/tennis/application/` — 25 проверок участников, прав, черновиков и миграции.
- `src/test/kotlin/ru/movereon/tennis/telegram/` — 48 проверок диалогов и HTTP-клиента с подставным API и локальным сервером. Всего проходят 113 тестов.

`GroupService` проверяет права на финансовые и организационные действия. Telegram-адаптер создаёт `VerifiedGroupMember` по реальному отправителю обновления и результату `getChatMember`. Для представительства ушедшего участника отдельно проверяется отсутствие в чате. Команды кнопок хранятся на сервере и привязаны к пользователю. `Actor` создаётся внутри прикладного слоя.

Профили, привязка Telegram ID, черновики, проверка дат и предупреждение о похожем переводе доступны через личные диалоги. Ответ на запрос суммы или времени принимается как ответ на конкретное сообщение-запрос. Реализация проверена локально; поведение реальных клиентов Telegram предстоит проверить на пробной тренировке.

`JournalEvent` сохраняет финансовое влияние и автора. `SqliteAccountingStore` дополнительно сохраняет полные исходные команды, даты и пояснения, результат команды и событие очереди. При повторном открытии восстанавливается сохранённое финансовое состояние, а не заново вычисляются доли старых тренировок. Привязки и остальные действия прикладного слоя записываются в `workflow_audit`; публикация черновика, финансовый журнал и оба результата команд фиксируются атомарно.

## База и следующий этап

Выбрана SQLite для первого запуска одного сервиса. Используется JDBC-драйвер Xerial 3.53.2.1 и `kotlinx.serialization` 1.9.0 для формата хранения. Отдельный сервер базы не требуется. Доступ идёт через JDBC; дополнительный слой ORM не добавлен. Ядро не зависит от SQLite, но перенос на PostgreSQL потребует отдельного адаптера и миграции данных.
