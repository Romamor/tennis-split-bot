# Мониторинг виртуалки в Grafana Cloud

Статус: локальный сбор на сервере запущен. Alloy 1.19.2 и дополнительный таймер
работают автоматически; проверены 196 рядов метрик и все необходимые показатели
памяти. В прогретом локальном режиме Alloy занимал около 43 МиБ без перезапусков.
Отправка в Grafana Cloud, импорт панели и уведомления ещё не подключены: нужны
реквизиты приёма метрик облачного аккаунта. Наличие файла панели не означает,
что она уже создана и проверена в Grafana.

Целевая схема: собирать метрики Linux раз в минуту через Grafana Alloy, хранить историю
в Grafana Cloud. Дополнительно нужны ballooning VMware и память контейнера бота.
Журналы, база, переписка и переменные окружения контейнера не отправляются.
Перед постоянным запуском требуется измерить расход памяти самого сборщика.

## Дополнительные показатели

`collect_extra.py` читает `/sys/kernel/debug/vmmemctl`, состояние указанного
контейнера и его cgroup v2. Он не читает окружение Docker. На выходе — числовые
метрики без реальных имён контейнеров и идентификаторов пользователей:

- `vds_balloon_current_bytes`, `vds_balloon_target_bytes` — удерживаемая и
  запрошенная VMware память; страницы умножаются на фактический размер страницы.
- `vds_bot_running`, `vds_bot_oom_killed`, `vds_bot_restart_count` — состояние бота.
- `vds_bot_memory_bytes`, `vds_bot_swap_bytes` — RAM и swap контейнера.
- `vds_balloon_collector_success`, `vds_bot_collector_success` — успешность чтения.
- `vds_extra_sample_timestamp_seconds` — время последнего запуска сборщика.

Неудачное чтение не заменяется нулевым потреблением: соответствующие показатели
не публикуются, флаг успешности равен нулю. Файл заменяется атомарно, чтобы Alloy
не прочитал половину записи. Чтение Docker и debugfs требует прав; доступ
основного процесса Alloy к Docker socket не планируется.

Локальные проверки:

```sh
python3 -m unittest discover -s deploy/monitoring -p 'test_*.py'
```

Проверены выбор текущего счётчика ballooning, отсутствие ложных нулей при сбое
и удаление устаревших показателей при атомарной замене файла.

Параметры облачного аккаунта и ключи не входят в Git. Установка и включение
передачи данных будут описаны после получения реквизитов подключения.

Источники: [Linux Server integration](https://grafana.com/docs/grafana-cloud/observe-and-act/monitor-infrastructure/integrations/integration-reference/integration-linux-node/),
[сборщик textfile](https://grafana.com/docs/alloy/latest/reference/components/prometheus/prometheus.exporter.unix/#textfile).

## Конфигурации и ограничения

- `config.local.alloy` — проверенный локальный режим, `forward_to=[]`, без
  передачи данных в облако. Служебный HTTP-интерфейс слушает только localhost.
- `config.cloud.alloy` — шаблон отправки в заданный HTTPS-приёмник. Требует
  GRAFANA_CLOUD_METRICS_URL / USER / TOKEN; ключу достаточно `metrics:write`.
- `alloy-limits.conf` — мягкая цель Go 64 МиБ, MemoryHigh 96 МБ, MemoryMax 128 МБ,
  MemorySwapMax 32 МБ, CPUQuota 20%. Расход после включения облачной очереди нужно
  измерить повторно; локальный замер его не гарантирует.
- `vds-extra-metrics.service` / `.timer` — чтение дополнительных показателей
  раз в минуту. Имя контейнера задано в закрытом `/etc/vds-monitoring/collector.env`.
- `vds-memory.dashboard.json` — панель для импорта с выбором Prometheus-источника.
  `build_dashboard.py` воспроизводит её; 13 блоков памяти, ballooning, PSI,
  swap, CPU, диска и проверки поступления показателей.

Временная очередь Alloy сохраняет данные перед отправкой на диск. Для облачного
шаблона заданы очистка каждые 15 минут и максимальный возраст 1 час; это ограничение
возраста, а не точный предел размера файла. При более долгой недоступности
облака старые неотправленные показатели могут быть потеряны.

После установки официального пакета служба сначала была заблокирована от запуска,
затем проверена локальная конфигурация и включены Alloy и таймер. Исходная
конфигурация пакета сохранена отдельно. Службы бота и Docker не перезапускались;
входящие порты не открывались. Анонимная телеметрия Alloy отключена
`--disable-reporting`. Для постоянного запуска используется:

```sh
alloy run --disable-reporting --server.http.listen-addr=127.0.0.1:12345 \
  --storage.path=/var/lib/alloy/data /etc/alloy/config.alloy
```

## Следующий шаг: подключение облака

В своём Grafana Cloud найти Linux Server integration / настройку отправки метрик.
Нужны URL приёма Prometheus remote write, идентификатор пользователя метрик
и отдельный ключ с правом записи метрик. Пароль аккаунта не используется.
Реквизиты вносятся в закрытый файл вне Git; до включения отправки проверяются
адрес назначения, конфигурация и права файла. Токены не добавляются в команды,
скриншоты, публичные документы и журналы.

После подключения требуется подтвердить поступление метрик в облако,
импортировать панель и проверить временные ряды. Затем отдельно настраивается
получатель уведомлений и тестируется доставка. Пока эти шаги не выполнены,
считать мониторинг с оповещениями готовым нельзя.
