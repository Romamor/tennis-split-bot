# VPN: состояние, ресурсы и трафик

Статус: серверный сбор и передача в Grafana Cloud проверены.
Обновлённая панель готова к повторному импорту пользователем; её отображение
в его Grafana ещё не подтверждено. Предлагаемые VPN-уведомления не созданы.

Добавлен раздел VPN в существующую панель «VDS · память и VMware». Первые 13
блоков сохранены. Ни подключение VPN с другой машины, ни настройки туннелей
этим изменением не затрагиваются. Внешняя проверка соединения остаётся отдельным этапом.

## Что собирается

Для каждого настроенного VPN публикуется короткий псевдоним `vpn`, например
`vpn-1`. Соответствие псевдонимов контейнерам и туннельным интерфейсам находится
в закрытом `/etc/vds-monitoring/collector.env`, а не в Git или метках Grafana.

| Метрика | Значение |
| --- | --- |
| `vds_vpn_running` | Контейнер запущен: 1 или 0 |
| `vds_vpn_collector_success` | Удалось прочитать состояние и показатели |
| `vds_vpn_memory_bytes`, `vds_vpn_swap_bytes` | RAM и swap cgroup контейнера |
| `vds_vpn_cpu_seconds_total` | Суммарное процессорное время в секундах |
| `vds_vpn_cpu_throttled_seconds_total` | Ожидание квоты CPU, если счётчик доступен |
| `vds_vpn_restarts_total` | Счётчик перезапусков Docker |
| `vds_vpn_oom_killed` | Последняя остановка отмечена Docker как OOM |
| `vds_vpn_oom_kills_total` | События OOM в текущей cgroup |
| `vds_vpn_receive_*_total`, `vds_vpn_transmit_*_total` | Байты, пакеты, ошибки и отброшенные пакеты туннельного интерфейса |

Трафик берётся только с выбранного туннельного интерфейса. Суммирование его
с внешними интерфейсами контейнера повторно учитывало бы те же данные.
Отдельный график сети виртуалки использует `node_network_*` от Alloy; loopback,
мосты Docker и виртуальные соединения контейнеров исключены. Графики туннелей
и сети хоста тоже не нужно складывать. Скорость показана в байтах в секунду;
это фактический трафик, а не результат измерения максимальной пропускной способности.

Число 100% на графике CPU соответствует одному логическому ядру. Часть сетевой
обработки выполняется ядром Linux, поэтому рядом остаётся общий график CPU.

При остановке контейнера сохраняются состояние и счётчик перезапусков, а прежние
показания RAM, CPU и сети больше не публикуются. При ошибке чтения нет ложного
нуля: `collector_success=0`, показатели отсутствуют. Ошибка одного VPN не мешает
собирать остальные VPN и данные бота. Существующее правило устаревания
дополнительных метрик контролирует общий таймер.

Счётчики обнуляются при пересоздании контейнера или cgroup. `rate` и `increase`
учитывают сброс, но не восстанавливают события, произошедшие между опросами.
В частности, быстрый OOM с перезапуском может не попасть в минутный снимок.
Состояние running не подтверждает доступность VPN извне или успешное соединение клиента.

## Настройка

`VPN_CONTAINERS` содержит JSON с двумя обязательными полями для каждого псевдонима.
Искусственный пример для EnvironmentFile systemd:

```ini
VPN_CONTAINERS='{"vpn-1":{"container":"sample-vpn","interface":"wg0"}}'
```

Контейнеры и интерфейсы сначала определяются на целевом сервере. Не выбирать
интерфейс только по номеру eth0: у VPN может быть несколько сетей.
Сборщик не читает ключи VPN, списки клиентов, адреса подключений или содержимое пакетов.
В Grafana отправляются агрегированные числовые показатели.

После изменения выполнить локальные проверки, проверить конфигурацию Alloy с
закрытым EnvironmentFile, сохранить предыдущие файлы и обновить сборщик и
службу vds-extra-metrics. Таймаут увеличен до 35 секунд для нескольких опросов
Docker (по 8 секунд максимум), интервал остаётся минутным. Перезапускать VPN
или бота не нужно; конфигурация Alloy перечитывается через reload.

## Панель Grafana

Снова импортировать `vds-memory.dashboard.json` в тот же проект. UID `vds-memory`
сохранён — существующая панель обновляется с подтверждением замены. Выбрать тот
же источник Prometheus. Получается 21 панель показателей и одна строка раздела.
Если пользователь уже менял панель самостоятельно, сначала экспортировать её,
чтобы сохранить свои изменения. Графикам скорости нужно несколько минут данных.

## Предлагаемые уведомления VPN

Эти правила ещё не созданы в Grafana. Использовать прежнюю папку VDS, группу
оценки vds (1m) и получателя личного Telegram. Для запроса выбрать Code.

**«VPN остановлен или не читается»** — Last IS BELOW 1, Pending 1m:

```promql
min by (instance, vpn) (
  {__name__=~"vds_vpn_running|vds_vpn_collector_success",instance="vds-1",job="integrations/node_exporter"}
)
```

**«Частые перезапуски VPN»** — Last IS ABOVE 2, Pending 0s:

```promql
increase(vds_vpn_restarts_total{instance="vds-1",job="integrations/node_exporter"}[15m])
```

**«VPN завершён из-за нехватки памяти»** — Last IS ABOVE 0.5, Pending 0s:

```promql
vds_vpn_oom_killed{instance="vds-1",job="integrations/node_exporter"}
```

Последнее правило опирается на доступный снимок Docker, а не на полный журнал
событий. Все правила нужно проверить в Preview перед сохранением. Получение
новых VPN-уведомлений пока не проверено; прежний тест канала Telegram этого не заменяет.

## Проверки

Девять проверок Python включают выбор единственного сетевого интерфейса,
единицы CPU, остановленный контейнер, независимость ошибок VPN, отсутствие ложных
нулей и правильное описание счётчиков Prometheus. Проверено, что прежние панели
не изменились, номера новых панелей уникальны и их области не пересекаются.
